# Разбор проекта для защиты

Читать сверху вниз, по одному модулю. После каждого модуля закрыть файл и ответить на вопросы вслух, не подглядывая.

## Путь одного вопроса

Пользователь вводит вопрос на странице `app/ui/index.html`. Страница шлёт запрос в `/api/ask`, тот вызывает `Engine.investigate` (`app/engine.py`). Тот создаёт `Investigator` (`app/rag/answer.py`). Планировщик (`app/rag/planner.py`) просит LLM разбить вопрос на поисковые запросы. По каждому запросу `HybridSearcher` (`app/search/hybrid.py`) ищет в Qdrant по вектору и в BM25 по словам и сливает два списка через RRF. Найденные чанки получают метки C1, C2 и уходят в LLM вместе с вопросом. LLM либо просит ещё поиск через инструмент `search_documents`, либо возвращает JSON с ответом, метками цитат, противоречиями и флагом нехватки данных. Сервер выкидывает метки, которых не показывал, и отдаёт результат обратно в интерфейс.

## 1. Загрузка (`app/ingest/loaders.py`)

Каждый формат читается своей функцией. PDF через pypdf постранично, DOCX через python-docx по абзацам, TXT и MD как текст. Потом текст нормализуется (одинаковые переводы строк, не больше одной пустой строки подряд). `doc_id` строится из имени файла, поэтому повторная загрузка файла с тем же именем считается обновлением.

Вопросы. Почему `doc_id` из имени, а не из содержимого? Что будет со сканом PDF без текстового слоя? Где хранятся метаданные и зачем они?

Ответы. Из содержимого нельзя было бы отличить «новую версию» от «нового документа». Скан даст пустой текст, и загрузчик честно откажет с ошибкой, OCR не входит в объём. Метаданные лежат в payload Qdrant у каждого чанка и показываются в интерфейсе.

## 2. Чанкинг (`app/ingest/chunking.py`)

Стратегия A режет текст окнами фиксированной длины с перекрытием и не рвёт слова. Стратегия B держит абзацы целыми, склеивает короткие и режет стратегией A только слишком длинные. В индекс и в эмбеддинг идёт `title + text`, потому что короткий абзац без заголовка теряет смысл.

Вопросы. Зачем перекрытие? Почему в HotpotQA стратегии почти не отличаются при размере 800? Что хуже, слишком крупный или слишком мелкий чанк?

Ответы. Перекрытие спасает факт, который попал на границу двух окон. Абзацы HotpotQA короче 800 символов, поэтому сравнение делается с A на 300 символах. Крупный чанк размывает эмбеддинг несколькими темами, мелкий теряет контекст, выбор подтверждаем метриками.

## 3. Дубли, добавление, обновление, удаление (`dedup.py`, `pipeline.py`)

Хэш SHA-256 берётся от текста без учёта регистра и пробелов. Таблица решений записана в docstring `IngestPipeline.ingest`. Тот же `doc_id` и тот же хэш значит «без изменений». Тот же `doc_id` и новый хэш значит обновление, старые чанки удаляются целиком, чтобы не осталось хвостов. Новый `doc_id` и уже известный хэш значит дубль.

Вопросы. Почему при обновлении сначала удаляем все чанки документа? Почему id точки в Qdrant это uuid5? Что будет при переиндексации того же корпуса?

Ответы. Новая версия может дать меньше чанков, и старые лишние остались бы в поиске. Qdrant принимает только UUID или число, а uuid5 из `chunk_id` всегда даёт один и тот же UUID. Поэтому переиндексация перезаписывает точки и не плодит копии.

## 4. Векторный поиск (`embeddings.py`, `vector_store.py`)

bge-small превращает текст в вектор из 384 чисел локально, без API. Для запросов fastembed добавляет префикс-инструкцию, которую ждёт модель bge. Qdrant ищет ближайшие векторы по косинусу. Все вызовы Qdrant идут через `_call`, где сетевые ошибки и 5xx повторяются, а остальное превращается в понятную `VectorStoreError`.

Вопросы. Почему Qdrant Cloud, а не файл на хостинге? Что значит косинус 0.9? Почему запрос и документ эмбеддятся разными методами?

Ответы. Диск бесплатного хостинга стирается при перезапуске. Косинус около 1 значит, что векторы смотрят в одну сторону, тексты близки по смыслу. bge обучена с инструкцией для запросов, без неё качество поиска ниже.

## 5. Ваше задание. BM25 (`app/search/bm25.py`)

Формула в docstring. Порядок работы такой. В конструкторе пройти по всем чанкам, токенизировать `search_text`, посчитать для каждого чанка `Counter` слов и длину, посчитать среднюю длину и для каждого слова число чанков, где оно встречается. Отсюда idf. Удобно сразу построить обратный индекс «слово → номера чанков», тогда поиск проходит только по чанкам с нужными словами, а не по всем 60 тысячам. В `search` для каждого слова запроса сложить вклад в счёт каждого чанка из обратного индекса, отсортировать по убыванию, взять k. Запустить `pytest tests/test_bm25.py`.

Вопросы. Что делает k1? Что делает b? Зачем `+ 1` внутри логарифма idf?

Ответы. k1 ограничивает вклад повторов слова, десятое повторение почти ничего не добавляет. b штрафует длинные чанки, иначе они выигрывали бы просто числом слов. Без `+ 1` слово, которое есть больше чем в половине чанков, дало бы отрицательный idf.

## 6. Ваше задание. RRF (`reciprocal_rank_fusion` в `app/search/hybrid.py`)

Для каждого списка пройти с номером позиции от 1, прибавить к счёту чанка `1 / (k + позиция)`. Отсортировать по счёту. Тесты в `tests/test_hybrid.py`.

Вопросы. Почему не складываем сами оценки двух поисков? Зачем k = 60? Что даёт чанку попадание в оба списка?

Ответы. Косинус от 0 до 1 и BM25 от 0 до десятков несравнимы. k сглаживает разницу между первыми местами, первое место не забирает всё. Чанк из обоих списков получает две добавки и поднимается выше.

## 7. LLM и ошибки (`app/rag/llm.py`, `app/retry.py`)

Один клиент для любого OpenAI-совместимого API. Таймаут, 408, 429 и 5xx повторяются с паузой 1, 2, 4, 8 секунд плюс небольшой случайный разброс. Если сервер прислал Retry-After, ждём не меньше. Ошибки 401 или 400 не повторяются, это наша ошибка, повтор не поможет. После всех попыток API отдаёт клиенту 503 с понятным текстом.

Вопросы. Зачем случайный разброс в паузе? Почему 401 не повторяем? Что увидит пользователь при падении Groq?

Ответы. Чтобы много клиентов не повторяли запрос одновременно. Неверный ключ не исправится сам. Сообщение «модель сейчас недоступна» вместо зависания или трейсбэка.

## 8. Расследование (`planner.py`, `answer.py`, `tools.py`, `prompts.py`)

Планировщик всегда ставит исходный вопрос первым, потом подвопросы. Если план сломался, ищем по самому вопросу. Контекст это не больше 12 чанков с метками. Модели разрешены 2 раунда инструмента поиска, на последнем раунде инструменты не передаются, чтобы она обязательно ответила. Затем проверка цитат и флагов.

Вопросы. Как система отказывается отвечать? Как ловится выдуманная цитата? Как защищаемся от инструкций внутри документов?

Ответы. Модель ставит `insufficient_evidence`, а сервер ставит его сам, если не осталось ни одной честной цитаты. Метки сверяются со словарём показанных чанков. Промпт говорит, что текст чанков это данные, а в синтетике есть документ с такой атакой для проверки.

## 9. Ваше задание. Метрики (`eval/metrics.py`)

Recall@K это доля релевантных документов среди первых K. Reciprocal rank это `1 / позиция` первого релевантного или 0. Citation accuracy это доля процитированных документов, которые релевантны. Тесты в `tests/test_metrics.py`.

Вопросы. Чем Recall@K отличается от MRR? Почему считаем по документам, а не по чанкам? Почему citation accuracy это точность, а не полнота?

Ответы. Recall говорит, нашли ли вообще, MRR говорит, насколько высоко. В HotpotQA разметка дана по статьям, а у статьи может быть несколько чанков. Нам важнее, что каждая ссылка честная, а полноту поиска уже меряет Recall.

## 10. API, интерфейс, деплой

FastAPI отдаёт `/api/*` и HTML-страницу на корне, это один процесс. Хостинг — бесплатный Render с лимитом 512 МБ (ADR 0008), поэтому BM25 хранится в массивах numpy, а тексты чанков не держатся в памяти и подтягиваются из Qdrant. При старте `Engine` в фоне читает все чанки из Qdrant и строит BM25. Ключи только в секретах Render.

Вопросы. Что произойдёт при перезапуске сервиса на Render? Где лежат ключи? Почему эмбеддинги корпуса не считаются на хостинге?

Ответы. Данные в Qdrant Cloud, BM25 пересоберётся при старте. В секретах Render и в локальном `.env`, который в `.gitignore`. Бесплатный CPU считал бы 60 тысяч эмбеддингов слишком долго, это делается один раз на ноутбуке.
